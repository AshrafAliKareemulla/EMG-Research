  EMG channel semantics (this matters when combining datasets)

  - cols 1-8: eight electrodes equally spaced around the forearm at the radio-humeral joint (dense sampling)
  - col 9: Flexor Digitorum Superficialis main activity spot (palpated)
  - col 10: Extensor Digitorum Superficialis main activity spot
  - col 11: Biceps Brachii
  - col 12: Triceps Brachii

  So channels 1-8 are spatial/topological; channels 9-12 are anatomical. Other Ninapro DBs and EMAHA/BioPatRec do not
  share this layout — keep this in mind for cross-dataset training.

  stimulus vs restimulus — pick one deliberately

  - stimulus = the label the video told the subject to do. Off by a human reaction-time amount (often 100-300 ms).
  - restimulus = same label after offline GLR (Generalized Likelihood Ratio) realignment that maximizes likelihood of a
  rest-movement-rest sequence. This is the label used by virtually all DB2 benchmarks (P2 paper, EMGHandNet, etc.).

  Recommendation: use restimulus / rerepetition and clearly document. Both papers use restimulus.

  Per-file label space ⚠️ subtle trap

  The label values restart at 1 in each E-file:
  - S1_E1_A1.mat → restimulus ∈ {0, 1..17} (rest + 17 hand/wrist movements)
  - S1_E2_A1.mat → restimulus ∈ {0, 1..23} (rest + 23 grasps/functional)
  - S1_E3_A1.mat → restimulus ∈ {0, 1..9} (rest + 9 force patterns — not classification, regression target)

  To get the canonical "DB2 49-class" or "DB2 40-movement-class" label space, you must offset E2 labels by +17. E3
  should usually be excluded from the classification task (it's force regression). So a unified label vector is:
  y_unified = restimulus_E1                        # values 0, 1..17
  y_unified = restimulus_E2 + 17 * (restimulus_E2 > 0)   # values 0, 18..40
  (Keep 0 → 0 for rest — don't shift the rest class.)

  Standard benchmark protocol (both papers agree)

  - Window length: 400 ms (= 800 samples @ 2 kHz). P1 used 200 ms, but P2/DB2 settled on 400 ms.
  - Window stride: 10 ms (= 20 samples). Heavy overlap (97.5%).
  - Train/test split: repetitions 1, 3, 4, 6 = train; 2, 5 = test. This is by-repetition within a subject.

  2. How to segment, and how to verify labels are correct

  Two policies for windowing:

  (a) "Pure-class" windows (recommended for DB2 benchmarks):
  A window is kept only if restimulus[start : start+L] is constant. This drops the brief transition windows that span
  rest→movement. Almost all Ninapro papers do this implicitly by using restimulus-segmented epochs.

  (b) "Majority label":
  Take the mode of restimulus[start : start+L] as the window label. Looser, more samples, but mixes transitions.

  Verification recipe (do this once for subject 1, before you trust any pipeline)

  1. Sample-rate check: len(emg) / 2000 should be ~904 s for S1_E1_A1.
  2. Movement-block count: np.sum(np.diff(restimulus.flatten()) != 0) ≈ 2 × (movements × reps) = 2 × (17 × 6) = 204
  transitions for E1. If you also see boundary edges, expect 204 or 205.
  3. Per-class duration: For each k ∈ 1..17, count (restimulus == k).sum() / 2000. Should be ~5 s per repetition × 6
  reps ≈ 30 s ± noise.
  4. Rest duration: (restimulus == 0).sum() / 2000 should be roughly 17 × 6 × 3 ≈ 306 s, plus block boundaries.
  5. Visual sanity: pick one repetition of one movement, plot the 12-channel EMG with restimulus overlaid. EMG bursts
  must align with restimulus != 0 regions. If you see EMG burst starting before restimulus flips to non-zero by ~150-300
   ms, you're plotting stimulus, not restimulus — that's the reaction-time gap GLR was designed to remove.
  6. rep × class 2D table: build a (num_classes, 6) matrix counting samples per (class, rep) — should be roughly
  uniform.

  If all six pass, the label↔signal association is correct.

  3. Design flaws / things to fix in your HDF5 batching plan

  Your shape (num_signals, num_channels, segment_length) is on the right track but has gaps. Going through each concern
  carefully:

  (a) Schema is missing labels and metadata — biggest issue

  You can't shape it as (N, C, L) alone. At minimum you need parallel arrays:
  - X: (N, C, L) signals
  - y: (N,) class label (canonical/unified id)
  - subject_id: (N,) — required for LOSO, which is in your USER-REQUIREMENTS
  - repetition_id: (N,) — required to reproduce the official train/test split
  - exercise_id: (N,) — required to filter E1/E2 separately
  - dataset_id: (N,) — when you start mixing datasets
  - window_start: (N,) original sample offset, for traceability/debugging

  Without these, the prepped data is a one-shot dead-end — you can't redo splits or run LOSO.

  (b) Storing overlapping windows materialized = huge disk waste

  At 400 ms / 10 ms stride, you store every sample ~40× over. DB2 raw EMG-only is ~10 GB; materialized at 97.5% overlap
  → ~400 GB. With glove + acc it's multiples worse.

  Better pattern (used by MNE, torchaudio, every serious bio-signal pipeline):
  - Store the raw continuous signals once per subject (compressed HDF5 with gzip or lzf).
  - Store an index manifest (a small Parquet/CSV of ~1-10 MB) listing all valid window starts: (dataset_id, subject_id,
  exercise_id, repetition_id, file_path, start_sample, label).
  - The PyTorch Dataset.__getitem__(i) reads manifest[i], opens the HDF5, slices [start : start+L] on demand. HDF5
  chunked reads are fast (~µs).
  - You can change window length / stride / overlap by regenerating the manifest in seconds — no re-prep.

  This is exactly what an "indexed approach" should be — your instinct is right, but materializing windows defeats it.

  (c) "Keep all batches in system RAM" doesn't scale

  Even pre-extracted features for all of Ninapro DB2 + DB1 + DB5 + EMAHA at 400ms/10ms is hundreds of GB. With the
  manifest pattern above, RAM holds only the manifest (≪100 MB) and the workers stream from disk. PyTorch
  DataLoader(num_workers=8) will saturate any modern SSD.

  (d) Cross-dataset shape mismatch

  You won't get a single (N, C, L) schema across datasets unless you decide ahead of time:
  - C (channels): DB1=10, DB2=12, DB3=12, DB5=16, EMAHA varies, BioPatRec varies. Options: zero-pad to max C with a
  channel-validity mask; or keep per-dataset and use dataset-aware sampling (clean, recommended for now).
  - Fs (sampling rate): DB1=100 Hz, DB2/DB3=2 kHz, DB5=200 Hz, EMAHA varies. A "250 ms" window means 25 samples (DB1) vs
   800 samples (DB2). Either resample all to a canonical Fs (e.g. 1 kHz — minor downsampling for DB2), or keep native Fs
   and have per-dataset L. Resampling to a canonical Fs is the only clean way to mix them in one batch.
  - Channel semantics: col 11 of DB2 is biceps; the same column in another DB is something else. Mixing without
  channel-role tags will hurt training. For ADL-Net this matters a lot.

  (e) "Split into 5-6 files per dataset" — split by what?

  Split by subject, one HDF5 file per subject, full stop. This is the only split that respects LOSO and avoids
  accidental cross-subject leakage when later regenerating manifests. 40 files for DB2, ~80 MB EMG-only each. Don't
  artificially merge or split arbitrarily.

  (f) Auxiliary modalities (acc, glove, inclin) decision

  P2 shows sEMG+ACC gives ~5% accuracy gain over sEMG alone. Don't drop ACC at ingestion time — store it alongside EMG
  in the same HDF5. You can choose to ignore it at the model level later. Glove and inclin can also be useful for some
  experiments and are cheap to keep.

  (g) Rest-class policy not specified

  ~37% of DB2 is restimulus == 0 (rest). Three legitimate choices:
  - include rest as class 0 (49-class problem; what P1/P2 actually report)
  - exclude rest entirely (40-class problem; common in many DL papers)
  - subsample rest to balance

  You must pick and document this before generating the manifest. Mixing studies with different rest policies
  invalidates comparisons.

  (h) Window boundary policy

  "Drop transition windows" vs "majority vote" — pick one. I'd recommend pure-class (drop transitions) for DB2; it's
  what the GLR realignment is designed to make work cleanly.

  (i) Per-channel normalization

  Z-score per channel, computed on the training set only (per the standard protocol — P2 §III-A). Stats must be saved
  alongside the manifest. Don't normalize on the full dataset before splitting — that's a leak.

  force and forcecal — only present in E3 files

  Your E1 screenshot does not show them. In S<s>_E3_A1.mat you'll additionally see:
  - force (N × 6): 4 finger-flexion strain gauges + 2 thumb axes
  - forcecal (2 × 6): rest baseline (row 1) and MVC max (row 2) per finger, used to normalize force to a [0, 1]
  proportion of MVC. Apply as force_norm = (force - forcecal[0]) / (forcecal[1] - forcecal[0]).

  Why every stream has the same N

  The maintainers super-sampled every channel to 2 kHz (linear interp for continuous streams, nearest-neighbor for label
   streams) so that (emg, acc, glove, inclin, stimulus, restimulus) are all aligned by row index = sample index at 2
  kHz. Time in seconds for row i is i / 2000. You do not need to do any resampling yourself.

  D. Critical caveats — read before writing any code

  1. Use restimulus + rerepetition, not stimulus + repetition. GLR realignment removes the 100–300 ms reaction-time gap.
   Every DB2 benchmark in the literature uses restimulus. If you accidentally segment using stimulus, your "movement"
  windows will start with rest data and your accuracy will look 5–10 % worse than published numbers.
  2. Label namespace per file. restimulus values restart at 1 in each E-file. To merge E1 + E2 into a unified 40-class
  label space:
  # E1 file: y = restimulus                   (values: 0, 1..17)
  # E2 file: y = where(restimulus == 0, 0, restimulus + 17)  (values: 0, 18..40)
  2. Do NOT shift the 0 (rest) class.
  3. Exclude E3 from movement-classification datasets. It's a force-regression task with completely different stimuli
  and a different ground truth (FFLS). Treat it as a separate experiment if you want it at all.
  4. Website discrepancy: "10 repetitions" is wrong. The actual DB2 files have 6. Trust the data:
  np.unique(rerepetition) will show {0, 1, 2, 3, 4, 5, 6} exactly.
  5. Glove is uncalibrated. The 22 CyberGlove columns are raw sensor counts, NOT joint angles. They are proportional to
  angles for a given subject (after a per-subject linear scaling). For DL where you z-score per channel anyway, this is
  fine. For interpretability or joint-angle plots, you'd need per-subject calibration which Ninapro deliberately did not
   perform.
  6. Movement amplitude depends on repetition (slightly). P1's MANOVA found a statistically significant
  repetition-amplitude relationship in some subjects (esp. for kinematics — 35 % of DB2 subjects). Implication: when
  splitting train/test by repetition (which is the standard), you don't have to worry, but be cautious if you ever try
  cross-repetition-fold-CV — repetition is not perfectly i.i.d.
  7. The 50 Hz notch is already applied to the released files (Hampel filter). Don't re-apply it. If you
  bandpass-filter, start from somewhere above 20 Hz and below 500 Hz for sEMG — typical: 4th-order Butterworth bandpass
  20–500 Hz, plus optional 50 Hz notch (already done, so optional).
  8. The pre-roll second or two of the file is rest. restimulus[0] is 0. Don't assume the file starts with movement.

  ---
  E. Segmenting DB2 — concrete strategy

  Two segmentation policies. Pick one and document.

  Policy 1 — "pure-class" windows (recommended for DB2 benchmarks):
  For window [i, i+L):
  keep window iff  restimulus[i:i+L]  is constant
  label = restimulus[i]   (which equals every value in the window)
  This drops the brief transition windows that span rest→movement. With L = 800 and stride = 20 samples, you'll lose ~3
  % of windows to transitions; the rest are clean.

  Policy 2 — "majority-label" windows:
  label = mode(restimulus[i:i+L])
  keep all windows
  Looser, includes some transition windows. Many DL papers use this.

  For both policies: explicitly decide:
  - Stride: 10 ms (literature standard) for DL training; you may want 100 ms or 200 ms for classical-ML feature
  pipelines (Track 1) to keep the dataset small.
  - Rest class: include 0 as a class (→ 41 classes for E1+E2 combined, 18 for E1 alone) OR drop rest windows entirely (→
   40 classes for E1+E2). Both papers report numbers including rest. Recommendation: keep rest as class 0 — this is what
   published numbers compare against.

  Expected window count for subject 1, E1 alone (sanity number)

  - Movement samples: 17 movements × 6 reps × 5 s × 2000 Hz = 1,020,000 samples
  - Rest samples: ~788,000 samples
  - Pure-class windows at L=800, stride=20: roughly (1808331 − 800) / 20 ≈ 90,400 windows total, of which ~3 % are
  dropped as transitions, leaving ~88,000 windows.

  Scale that up: 40 subjects × E1+E2 ≈ ~7 million windows at L=800, stride=20. You will not store that materialized; see
   §G.

  import numpy as np

  # 7. visual: plot emg[idx0:idx1, :] with restimulus overlaid for one (k, r) pair

  #    (it should NOT lead by 100–300 ms — that would mean you used `stimulus` not `restimulus`)

  trust the downstream pipeline.

  └───────────────────────────┴──────────┴───────────────────────────────────────────┘

  For all 40 subjects, EMG + labels only ≈ 6.3 GB. With all sensors ≈ 37 GB.

  Materialized windows at L=800, stride=20 (≈ 87,000 windows/subject, EMG only):
  87,000 × 12 × 800 × 4 B = 3.34 GB / subject → ~134 GB across DB2 just for EMG windows.

  This is the central efficiency observation. You have two clean choices:

  - Plan A — Raw signals + window manifest (recommended). One HDF5 per subject containing the raw float32 streams (emg,
  optionally acc, glove, inclin) plus the int8 restimulus/rerepetition. A small (~50 MB) Parquet manifest lists every
  valid window: (subject_id, exercise_id, file_path, start_sample, label, repetition_id). PyTorch Dataset.__getitem__(i)
   opens the HDF5, slices [start:start+L] — HDF5 chunked reads are microseconds. DB2 EMG-only fits in 6.3 GB on disk;
  manifest in ~50 MB. Window length / stride / pure-vs-majority can be changed by regenerating the manifest in seconds,
  no re-prep.
  - Plan B — Materialized windows. One HDF5 per subject (or per group of subjects) with shape (N_windows_in_file, 12,
  800) plus parallel y, repetition, subject. Disk: ~134 GB EMG-only. Simpler to read at training time, but: re-deciding
  window size means re-running the prep (hours), changing stride means re-running, adding majority-vote means
  re-running. Locks you in.

  On your "5–6 files for DB2" intuition:
  - If you do Plan A (raw): 40 files of 157 MB EMG-only is fine; or 8 files of ~5 subjects each is also fine. File count
   barely matters because the manifest abstracts it.
  - If you do Plan B (materialized): per-subject is cleanest for LOSO. Multi-subject grouping needs careful indexing
  per-subject within the file. 5–6 files means each file holds 7–8 subjects which is workable.

  There is no DB2-specific reason that 40 subjects is "too many to fit in one file". The disk constraint comes from
  materialized windows, not from raw data. The right design choice is determined by Plan A vs Plan B, not by the number
  of subjects.

  import scipy.io as sio
  import numpy as np
  m = sio.loadmat('S1_E1_A1.mat')

  assert abs(len(emg)/2000 - 904.16) < 1.0           # ~904 s

  assert set(np.unique(restim).tolist()) == set(range(0, 18))    # {0, 1..17}

  # 3. repetition namespace
  assert set(np.unique(rerep).tolist()) == set(range(0, 7))      # {0, 1..6}

  # 4. expected (class, rep) cells: 17 movements × 6 reps = 102
  pairs = set(zip(restim.tolist(), rerep.tolist())) - {(0,0)}
  assert len(pairs) == 102

  # 5. each (movement k, rep r) block is contiguous and ~5 s long
  for k in range(1, 18):
      for r in range(1, 7):
          idx = np.where((restim == k) & (rerep == r))[0]
          assert idx.max() - idx.min() == len(idx) - 1     # contiguous
          assert 9000 < len(idx) < 11000                   # ~5s @ 2kHz, allow ±0.5s

  # 6. each rest block (between movements) is contiguous and ~3 s long
  # 7. visual: plot emg[idx0:idx1, :] with restimulus overlaid for one (k, r) pair

  G. Storage math for DB2 specifically

  Per subject (E1+E2 only, the classification subset), float32:

  ┌──────────────────────────┬─────────┬─────────────────────────────────────────┐
  │          Stream          │  Cols   │    Bytes/subject (E1+E2 ≈ 3,200,000     │
  │                          │         │                samples)                 │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ emg                      │      12 │                                  154 MB │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ acc                      │      36 │                                  461 MB │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ glove                    │      22 │                                  282 MB │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ inclin                   │       2 │                                   26 MB │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ restimulus +             │      2  │                                    6 MB │
  │ rerepetition             │  (int8) │                                         │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ Total                    │         │                   ~930 MB raw / subject │
  ├──────────────────────────┼─────────┼─────────────────────────────────────────┤
  │ EMG-only + labels        │ 14 cols │                       ~157 MB / subject │
  └──────────────────────────┴─────────┴─────────────────────────────────────────┘

  For all 40 subjects, EMG + labels only ≈ 6.3 GB. With all sensors ≈ 37 GB.

  Materialized windows at L=800, stride=20 (≈ 87,000 windows/subject, EMG only):
  87,000 × 12 × 800 × 4 B = 3.34 GB / subject → ~134 GB across DB2 just for EMG
  windows.

  This is the central efficiency observation. You have two clean choices:

  - Plan A — Raw signals + window manifest (recommended). One HDF5 per subject
  containing the raw float32 streams (emg, optionally acc, glove, inclin) plus the
  int8 restimulus/rerepetition. A small (~50 MB) Parquet manifest lists every valid
  window: (subject_id, exercise_id, file_path, start_sample, label, repetition_id).
  PyTorch Dataset.__getitem__(i) opens the HDF5, slices [start:start+L] — HDF5 chunked
   reads are microseconds. DB2 EMG-only fits in 6.3 GB on disk; manifest in ~50 MB.
  Window length / stride / pure-vs-majority can be changed by regenerating the
  manifest in seconds, no re-prep.
  - Plan B — Materialized windows. One HDF5 per subject (or per group of subjects)
  with shape (N_windows_in_file, 12, 800) plus parallel y, repetition, subject. Disk:
  ~134 GB EMG-only. Simpler to read at training time, but: re-deciding window size
  means re-running the prep (hours), changing stride means re-running, adding
  majority-vote means re-running. Locks you in.

  On your "5–6 files for DB2" intuition:
  - If you do Plan A (raw): 40 files of 157 MB EMG-only is fine; or 8 files of ~5
  subjects each is also fine. File count barely matters because the manifest abstracts
   it.
  - If you do Plan B (materialized): per-subject is cleanest for LOSO. Multi-subject
  grouping needs careful indexing per-subject within the file. 5–6 files means each
  file holds 7–8 subjects which is workable.

  There is no DB2-specific reason that 40 subjects is "too many to fit in one file".
  The disk constraint comes from materialized windows, not from raw data. The right
  design choice is determined by Plan A vs Plan B, not by the number of subjects.

  H. Design flaws in your current plan (DB2-only)

  1. Schema (num_signals, num_channels, segment_length) is missing the labels and
  metadata. You cannot do LOSO, can't reproduce the standard rep 2&5 test split, can't
   debug without subject_id, repetition_id, exercise_id, window_start_sample stored
  alongside.
  2. Materialized overlapping windows waste ~20–40× disk (Plan B numbers above). For
  ONE dataset it's tolerable; the moment you scale you'll regret it. Plan A's raw +
  manifest is materially better and not more complex if you use a WindowDataset
  wrapper.
  3. No stated policy for stimulus vs restimulus. Lock this in: restimulus for DB2.
  4. No stated policy for rest-class handling. Lock this in: keep rest as class 0 to
  be comparable to published benchmarks.
  5. No stated policy for transition windows. Lock this in: pure-class for DB2 (drop
  transitions).
  6. No stated policy for normalization. Z-score per channel using stats computed only
   on the training repetitions (1, 3, 4, 6); save the stats with the dataset so
  they're reapplied identically at inference.
  7. No plan to merge E1 + E2 label spaces. You need the +17 offset rule for E2 (and a
   flag (exercise_id == 2) so you can always trace back).
  8. No plan for ACC. P2 shows EMG+ACC gives ~5 % accuracy gain. Don't drop ACC at
  ingestion; you can ignore it at the model later if you want EMG-only.
  9. "Keep all batches in RAM" doesn't scale even for DB2 alone if you materialize
  windows (~134 GB EMG-only). With Plan A the manifest is tiny; with Plan B you'd page
   from disk anyway. PyTorch DataLoader(num_workers=8, pin_memory=True) already does
  optimal streaming.
  10. No verification step in the plan. Step F above must run before any model is
  trained, and the result should be saved (e.g. as a verify_subject1.json artifact in
  the dataset folder).
